PHASE 05 · HEADLESS LOGIN Built 15 Oct · first live sign-in is the owner's

grokbot login — Own-Token Headless PKCE

The CLI now has its own sign-in, so it no longer needs the desktop app's token. It mirrors the app's real flow (fact 14): browser PKCE plus /auth/poll. It is not an email or phone OTP typed into the terminal, because that only exists on cursor.com's web page. An asc web auth login-style flow is not possible for GrokBot; this is the closest headless equivalent. The owner approved storing the sign-in in the Keychain (Rule 3 amended).

  1. The app's wire, exactly: auth-pkce.ts makes the pair (passes the RFC 7636 S256 test vector) and {website}/loginDeepControl?challenge&uuid&mode=login&redirectTarget=cli. URLs can be overridden only through GROKBOT_API_BASE_URL and GROKBOT_WEBSITE_URL (https only), so a global CURSOR_API_BASE_URL never redirects the refresh token.
  2. Poll like the app: auth-poll.ts calls GET /auth/poll?uuid&verifier. A 404 means keep waiting; it tries up to 150 times with a 1 s→10 s ×1.2 backoff, gives up after 3 non-404 failures in a row, stops on Ctrl-C, and maps a device-policy 403 to a clear error.
  3. Headless UX: grokbot login prints the link plus a terminal QR (uqr, MIT, no deps) and opens the browser; --no-browser is for remote machines. No email or phone is entered in the CLI.
  4. Keychain + silent refresh: auth-credential-store.ts keeps the pair in the Keychain item grokbot-cli via security -i (stdin, never argv). auth-token-source.ts uses that sign-in first and refreshes it through POST /oauth/token when under 5 min remain. It keeps rotated pairs, shares one refresh between concurrent calls, drops an ended sign-in and falls back to the app's token. A network blip keeps the saved pair.
  5. CI path: grokbot login --api-key reads GROKBOT_API_KEY or stdin, never argv, and calls POST /auth/exchange_user_api_key. grokbot logout and grokbot whoami (no token printed) complete the set. All three are CLI-only, so grokbot-mcp never offers them.
Done when: grokbot login signs the CLI in with the GrokBot app logged out, keeps the token in the Keychain, refreshes it on expiry, and a read-only grokbot agents works end to end. Status: built and unit-tested. Live checks so far: the login page answers 200, /auth/poll answers 404 (pending) for a cli pair, whoami reports the app's login, and agents is unchanged. Not yet proven: a full browser sign-in and a refresh, which need the owner at the browser.
PHASE 06 · BOTS TALK BACK TO CLAUDE Designed 16 Oct · parked the same day · not built

Two-Way: a Bot Can Reach Claude Unasked

Parked (owner, 16 Oct): no real problem needs it yet. Build only for a problem that has actually happened. The owner and Claude work as peers; GrokBot is the always-on assistant the owner follows from the phone. Going through the cases where the owner leaves while working with Claude:
  • Claude is still working: it keeps working while the Mac is on. That work matters enough that Claude does it, and a bot would not do it better, so nothing is handed over.
  • Claude stops to wait for the owner (a permission or a decision): a problem between the owner and Claude, solved by Claude's own notifications and Remote Control. Without Remote Control Claude just waits; nothing is lost.
  • The Mac sleeps or shuts down: keep the Mac awake while Claude works (the desktop app has this), or start long work as a cloud Claude session. Still Claude, not GrokBot.
Rejected along the way: a grokbot handoff command or a "brief Grok Bot before leaving" habit (a ritual the owner does not want), a separate cloud-agent command (Grok Bot already sends code work to Cursor cloud agents and Claude can already ask it), and letting Grok Bot open the Mac to see how far Claude got (weakest: no context, and a shell on the Mac). The split that stays: work that starts with Claude stays with Claude; work the owner gives from the phone, and routines, go to GrokBot. Revisit when the owner actually hits "Claude does not know what GrokBot did while I was away" and it hurts; then start with the smallest piece: a read-only grokbot summary of what changed since last time, fed to Claude by a Claude Code SessionStart hook, with no mailbox bot and no background program. The design below is kept for that day.

Today only Claude starts a conversation: it sends, waits and reads. When a bot needs something on its own (a decision, an approval, it is blocked, or a long task Claude gave it is done), nobody on Claude's side hears it. Phase 06 gives bots one address for Claude and gives Claude a way to receive, on the owner's Mac, in the right project folder, in a session the owner can open. The owner keeps chatting with bots in the app as before; those chats are never routed to Claude.

  1. Mailbox bot "Claude Inbox": a dedicated GrokBot bot. Other bots reach Claude with SendToAgent to it, the same way they message each other. It needs no new service or token, keeps every message on GrokBot's servers while the Mac is off, and the owner can read it in the GrokBot app, phone included. Its instructions say: reply with one word and do nothing else. The Done Rule must treat a message to the mailbox as answered at once: in the 16 Oct test its reply never reached the sender, so the sender's ask waited on it until it timed out.
  2. Teach every bot: a Box-wide skill reach-claude (pushed once with grokbot skills push) says when to message Claude, never to send secrets, not to wait, and the format: [<repo name>] <title>, Need: decision | approval | info | done, Details, Urgent. A skill loads only when a bot thinks it applies, so each bot's instructions also get one line pointing to it (grokbot update), and grokbot hire adds that line to new bots.
  3. Mac background program: starts at login (launchd), follows the Claude Inbox transcript from a saved cursor, so messages sent while the Mac was off are picked up when it comes back. No relay on another server and no second store: GrokBot's transcript is the store, the program keeps only "read up to here" and per-message state. The WatchGrokBotTranscripts stream, reconnects and the Done Rule are reused from grokbot-core.
  4. Find the project folder by git remote: the program maps repo name to local folder by reading the git remote of each folder in the owner's projects folder, with a hand-edited override file. Folder names are not reliable: one project's repo name differs from its folder name. When a message names no repo, or the repo has no local folder, a "dispatcher" Claude session in the projects folder reads it and picks the folder.
  5. One Claude session per task: the program runs Claude Code headless in that folder (claude -p, a fixed --session-id, later --resume), one session per bot and project, so follow-ups keep their context. Claude answers the bot with grokbot send. Headless Claude only does what is already allowed; anything that needs a permission waits for the owner. A daily wake limit, quiet hours and a pause switch apply.
  6. Busy, then wait: before resuming a session, the program checks its transcript file (~/.claude/projects/<folder>/<session-id>.jsonl). If someone other than the program wrote to it in the last 10 minutes, the owner is working in it: the program holds the message, shows a notification, and resumes the session with the held messages once it has been quiet for 10 minutes. A lock per session stops two headless runs writing at once.
  7. Open in Claude desktop: the owner opens any of these sessions in the desktop app with claude --desktop --resume <session-id> (Claude Code 2.1.285+, documented; local version 2.1.301), which continues the same session, or finds it with /resume in the desktop app. A session that is running headless cannot be moved until it stops.
Done when: a test bot asks for a decision while the Mac is asleep, the Mac picks it up on wake, Claude answers from the right folder, the test bot gets the answer, and the owner opens that session in Claude desktop. Not: a relay on another server, Claude running on a server out of the owner's sight, or a second message store. Fallbacks: a Slack channel (one thread per task) or email (the bots' own inboxes) can replace the mailbox bot; everything after "receive" stays the same.
PHASE 07 · EVENT ROUTINES Owner chose option B 17 Oct · built and tested live the same day

Event Routines: Wake a Bot Without Chatting

What it solves, and what it does not. A routine is a fixed prompt a bot runs on its own when its trigger fires. grokbot now creates and changes routines with any trigger, and fires webhook routines with a key kept in the macOS Keychain, so Claude, a script or CI can start a bot's routine without chatting. It pushes work into GrokBot; it does not return an answer: a run's own output cannot be read, so the routine's prompt must tell the bot where to post its result (the main chat, Slack or email). A bot reaching Claude unasked is Phase 06, which stays parked.
  1. Create and change through the bot: every bot of the owner runs on GrokBot's servers (harness temporal), where only the bot itself can save a routine, with its UpdateRoutine tool. So routines-create and routines-update send the bot one exact instruction (name, on or off, trigger as JSON, prompt between marker lines), wait for its turn with the Done Rule like ask, read the routine back and fail if anything differs. Flags: --cron, --webhook, --email <inbox> [--from …] [--require-auth-pass], --github <owner/repo> --events … [--ci-branch] [--pr], and --trigger or --trigger-file JSON for Slack, Microsoft Teams, Linear, Sentry, PagerDuty, Origin and groups, checked against the app's trigger shapes first; --paused and --timeout. Only a webhook routine went through this live; the other trigger kinds pass the shape check but were not run. A bot on the Cloud Box harness (none today) still goes through the Box Gateway, unverified: the read-back uses the server list, which may not hold such a bot's routines.
  2. No run-now on these bots: routines-run refuses on a temporal bot and points to routines-fire; the Box Gateway answered every runAgentAutomationNow with HTTP 409 automation-run-now/refused.
  3. Mint a webhook key: routines-webhook-key <bot> <routine> --yes calls DashboardService.CreateAutomationWebhookApiKey {automationId} (the server transport now takes a service; its tag lives in DASHBOARD_METHOD_SAFETY). It is sensitive and CLI only, refuses a routine without a webhook trigger, and mints only when no key is stored unless --replace.
  4. Key in the Keychain, never in a file: one item per routine, service grokbot-cli-webhook, account a hash of backend, bot and routine, written through security -i on stdin with the configured access mode. It stores the routine's createdAt, so a re-created routine never uses an old key. No output carries the key. routines-delete removes the item first.
  5. Fire: routines-fire <bot> <routine> [--payload <json> | --payload-file f.json] sends POST <backend>/automations/webhook/<automationId> with Authorization: Bearer <key> and returns the reply, {"success": true, "runUuid": …}. Tagged writes; the key is scrubbed from every error and reply.
  6. Keys for other machines (deferred): a caller without this Mac's Keychain needs the key in its own secret store, for example piped into gh secret set on stdin. Not built: the owner named no such caller (17 Oct).

Live on Primary Test, 17 Oct (owner's OK for the mint, the second mint and the deletes): the Box Gateway's createAgentAutomation wrote a routine file in the Box that the server never listed, and updateAgentAutomation returned OK but changed nothing, because a temporal bot's routines live on the server. The 14 Oct facts already said so ("Temporal bots use api2.cursor.sh for … routines"; "There is no create method"), and the design missed it. The chat path then created a paused webhook routine and renamed it, each checked on read-back. A minted key fired the routine (HTTP 200, a run with trigger event, status ok, about 6 s); a wrong key got HTTP 401 "Invalid API key". A second key did not revoke the first: both fired. After routines-delete the Keychain item was gone and the key got 401. All test routines and the orphan Box row were removed; Primary Test has no routines.

Done: bun run verify green; live steps above on Primary Test only. Not: a key in a file or in any output, routines on the main Grok Bot, a listener on Claude's side, or routines-fire --wait (a run's own output cannot be read; see Open Questions).

01 14 Oct 2026 · Standalone Boundary

100% Standalone, Host-Agnostic Workforce Engine

Grokbot-cli (grokbot-core, grokbotagent-cli, grokbot-mcp) is a standalone open-source toolset with no dependency on any host. Terminals, agent runtimes, and host apps integrate from outside through the CLI, the TypeScript SDK, or the MCP server. LilOS is one such consumer and owns its own integration code in its own repo.

Not: Coupling this repo to LilOS (or any host) internals, adding host-specific code paths, or building a web/Electron UI here.
02 14 Oct 2026 · Module Contract

Single Catalog in grokbot-core → CLI First, Auto-MCP Second

Define every GrokBot command once in grokbot-core. Render the grokbot CLI + CEO SKILL.md as the primary interface (every agent runtime speaks Bash natively with zero transport flakiness), and auto-expose grokbot-mcp as a thin 50-line wrapper over the same catalog.

Not: MCP-only (breaks when stdio drops or bloats context) or maintaining separate logic in CLI and MCP.
03 13–14 Oct 2026 · Org Hierarchy

Chairman (You) → CEO (Opus / Argon) → GrokBot 4.7 Staff & bc-*

You give business outcomes ("grow conversion on example-app", "clone niche X + ads"). Your CEO decides Do vs. Delegate, writes tight SOPs for GrokBot default employees and bc-* cloud coding agents, and audits their output before reporting to you.

Not: Chairman micro-managing individual GrokBot bots directly.

100 Per-Bot :DISPLAY Windows + Per-Bot /workspace/staff/<slug>

GrokBot gives each bot its own X11 display slot (:2..:100 in .sand-window-assignments.json) and state folder (~/agent-data/agents/<id>/). Because shell pwd is shared (/workspace), grokbot hire assigns each bot /workspace/staff/<slug>/ + /workspace/shared/.

Not: Letting all bots dump files randomly into the root of /workspace.

Swappable Runtimes (Claude Code, Hermes, Codex) × Frontier Models

Separate the agent runtime/harness (Claude Code via ACP/CLI, Hermes via its gateway/ACP, Codex, Pi) from the model driving it (Opus on Max login, Argon, etc.).

Not: Confusing agent runtimes (Hermes, Claude Code) with models (Opus, Argon, GrokBot default) or locking the company to one harness.

HTML-Only Docs in This Repo · No Usage Caps

Not: Scattering Markdown plans, reports, or journals across the repo.

  3. Usage log stays local and holds no content. ~/.grokbot/usage (0600, about 90 days) records only the fields listed in usage-log.ts: command, surface, caller label, outcome, error code, duration bucket, input names, bot kind, version, OS. One exception, approved by the owner on 15 Oct 2026: grokbot login keeps its own sign-in in the macOS Keychain item grokbot-cli, written through security -i on stdin so it never shows in ps.       • silent: any process of this macOS user reads it without a dialog. MCP and background agents need this.
      • prompt: macOS asks once per grokbot run.
      The setting lives in ~/.grokbot/grokbot-cli.json (0600, never holds a token).

App Login Is Browser PKCE, Not Terminal OTP

app.asar v0.70.2 · 15 Oct · Static

The GrokBot app never asks for an email or phone code itself. startLogin() in electron-main/main-app.cjs makes a PKCE pair (verifier = 32 random bytes, challenge = base64url SHA-256 of it) and a random uuid, then opens https://cursor.com/loginDeepControl?challenge&uuid&mode=login&redirectTarget=sand&supportsSelectedTeamLogin=true in the browser. Any email, password, 2FA or OTP happens on that web page. The app then polls GET {backend}/auth/poll?uuid&verifier (up to 150 tries, 1 s to 10 s backoff ×1.2; HTTP 404 means "not yet", 3 other errors in a row give up) until it returns {accessToken, refreshToken}. Renewal is silent: POST {backend}/oauth/token with grant_type=refresh_token and rotation handling (shouldLogout forces a re-login). A second path, POST /auth/exchange_user_api_key (Bearer API key), also returns the pair. The only "one-time code to the account" RPC is passkey enrollment (StartPasskeyEnrollment), which is not a sign-in. On 15 Oct the active access and refresh tokens both expired on 12 Dec 2026.
